# HSComm32 可移植本地服务器模块设计

## 目标

在 Local Forwarder 中新增独立的“本地服务器”模块，让 macOS 上的 Local Forwarder 提供 HSComm32 中可移植的本地 HTTP 服务能力：静态资源服务、`.d` 资源解码与缓存、旧式本地数据接口，以及 `/reqxml` 上游转发。

本地服务器与现有代理实例使用各自的配置、运行状态、日志、监听端口和启动/停止生命周期。用户可以同时运行它们；启动或停止本地服务器不会更改现有代理配置或状态。

## 现状与限制

- `hscomm32` 包含 32 位 Windows `.exe` 和 `.dll`，没有服务端源码。macOS 版本不执行或打包这些 Windows 二进制。
- `server.ini` 和 `ForwardServer.ini` 提供监听、HTTP 文档、转发和访问控制设置；配置导入按 Windows GBK/CP936 解码。原文件只读。
- Local Forwarder 已有可复用的 HTTP 监听、静态项目目录、`.d` RC4/gzip 处理、本地数据接口、缓存，以及 HTTP/TCP `/reqxml` 转发实现。
- 现有 TCP 桥负责向上游建立连接；它没有实现未知的 HSCOMM 私有入站协议，也不加载 HSComm32 DLL 模块。
- 当前 macOS 包的协议资源没有 Node.js 16 运行时；TZT bytecode 依赖该运行时。因此，要让打包后的 Mac 版独立完成 `/reqxml` 和 `.d` 解码，需要随包提供匹配架构的 macOS Node.js 16 运行时，或替换该旧运行时依赖。

首版只承诺可移植的 HTTP、静态资源、缓存和 `/reqxml` 能力。`DBMiddleWare.exe`、`AjaxEngine.dll`、`H5JY.dll`、`PSWCode.dll` 等二进制模块提供的专有行为不在首版范围内；若客户端依赖这些行为，需要另行获得源码或协议样本后设计兼容实现。

## 用户流程

1. 用户打开独立的“本地服务器”页面，选择 `hscomm32` 根目录。
2. 应用读取 `server.ini`、`ForwardServer.ini`，并默认将 `hscomm32/download` 设为静态资源目录。
3. 导入预览展示已识别的本地端口、默认文档、上游地址、访问范围和未映射字段。用户确认或编辑后保存；有歧义的字段不静默猜测。
4. 用户在该页面单独启动、停止本地服务器，并查看其状态、日志和配置错误。

选择的目录和运行配置写入 Local Forwarder 的应用数据目录。应用不修改 `hscomm32` 原始配置和资源，不将整个 `hscomm32` 目录复制进安装包或 Git。

## 架构

### 独立服务边界

- 新增独立的 `LocalServerManager`、配置存储和服务对象，不复用现有代理实例的配置记录或生命周期管理器。
- 在 Electron 主进程注册独立的 `localServer:*` IPC 通道；Renderer 只调用本地服务器专用 API。
- Renderer 增加“本地服务器”入口，提供导入/编辑配置、启动/停止、运行状态和日志面板。
- 本地服务器使用独立配置文件、缓存目录和日志缓冲区。它可复用 `HttpProxy`、`FileCache`、`TcpBridgePool` 等核心实现，但每个模块持有各自的实例和状态。
- 对共用核心增加的选项必须保持向后兼容；现有代理不传这些选项时，行为保持不变。

### 配置导入与保存

- 新增针对 HSComm32 的 INI 导入器，支持 UTF-8 与 GBK/CP936 解码，不执行配置内容。
- 将 `server.ini` 中确认兼容的监听端口、超时、HTTP 默认文档和目录访问设置映射到本地服务器配置。
- 将 `ForwardServer.ini` 中可识别的 IP/端口条目导入为候选上游。只有用户确认传输类型和 `/reqxml` 顺序后才启用；`NextTcpType`、`Actions` 等尚无可靠映射的字段保留在导入摘要中并提示手工确认。
- `AcceptAll`、`AcceptIPList` 显示为访问范围设置。默认监听 `127.0.0.1`；扩大到局域网时由用户明确启用并检查允许列表。
- 本地服务器配置单独原子写入 `userData/local-server.json`；不覆盖导入的 INI 文件。账号、令牌等敏感值在界面与日志中掩码。
- 用户可以选择其他资源目录；路径规范化后必须限制在所选根目录内，拒绝路径穿越。

### 请求流程

```text
客户端
  -> 本地服务器自己的 HTTP 监听端口
  -> 本地数据接口、/login 或 /reqxml 路由
  -> 本地静态资源 / 缓存下载 / 已确认的 HTTP 或 TZT TCP 上游
  -> .d 解码、响应整理
  -> 客户端
```

- 本地静态资源从用户选择的目录读取；根路径使用导入或编辑后的默认文档。
- 静态资源缺失时，只有启用下载缓存且配置了合法 HTTP/HTTPS 下载目标时才向上游取回并写入本地服务器专属缓存。
- `/reqxml` 按本地服务器自己的上游列表和确认后的链路顺序转发，不读取或修改现有代理实例的上游设置。
- `/reqlocal`、`/reqsavemap`、`/reqreadmap`、`/reqsavefile`、`/reqreadfile`、`/login` 使用本地服务器自己的值存储。

## 错误处理与隔离

- 端口占用只让本地服务器进入错误状态，并显示占用端口；不终止其他进程，也不影响原代理。
- 无效 INI、无法识别的上游配置、缺失资源目录、缓存失败、上游超时和 TZT runtime 缺失均显示具体错误和修复提示。
- 启动部分失败时，关闭本地服务器已创建的监听器和连接；停止操作只释放本地服务器资源。
- 默认仅绑定回环地址。用户启用局域网访问时，界面明确显示绑定地址和访问范围。
- 缓存写入使用原子替换并限制在本地服务器缓存目录；日志默认不记录完整请求体和敏感值。

## macOS 运行与打包

- 保留现有 Intel x64 与 Apple Silicon 构建入口。
- 为两个 macOS 架构提供匹配的 Node.js 16 TZT helper 运行时，放入 `resources/protocol` 并纳入包内容校验；不得在 macOS 包中选择 Windows `node.exe`。
- `hscomm32` 由用户在本机选择，安装包只包含应用代码和协议运行时，不含该目录内的日志、配置、网页资源、`.exe` 或 `.dll`。

## 验收标准

1. 原代理保持现有配置与行为；可与本地服务器在不同端口同时启动。
2. 启动/停止本地服务器不会启动、停止、重配或清理原代理实例；反向操作也成立。
3. 导入 Windows 编码的 INI 后能正确读取已支持字段；有歧义或不支持的字段在启动前明确展示。
4. Mac 本地服务器能读取选定的 `download` 目录，服务普通资源和可解码的 `.d` 资源；缓存和路径穿越保护正常。
5. `/reqxml` 能按本地服务器独立的 HTTP/TCP 上游配置完成请求与响应。
6. 端口占用和上游失败只影响本地服务器，并显示可操作错误。
7. Intel x64 与 Apple Silicon 打包版本均能找到本架构 TZT runtime；运行时缺失时不会误加载 Windows 资源。
8. HSComm32 的 Windows DLL 专有行为明确标记为不支持，不伪装成已兼容。

## 测试范围

- INI：GBK/UTF-8、键值解析、重复键、无效端口、IP/端口数量不匹配、未知字段保留和导入预览。
- 隔离：原代理和本地服务器分配独立端口时并行启动；分别停止其中一个后，另一个继续响应；共享端口冲突只报告错误。
- HTTP：静态资源、默认文档、本地数据 API、变量替换、请求大小限制、上游超时与错误映射。
- 资源：本地 `.d` 解密、gzip、缓存命中/未命中、下载失败清理和目录穿越拒绝。
- `/reqxml`：HTTP/TCP 假上游、目标选择、序列号关联、超时、断线和停止清理。
- Electron：独立 IPC 白名单、配置重启恢复、日志脱敏以及 Mac x64/arm64 打包资源检查。
